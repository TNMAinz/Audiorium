# Feature status

Status vocabulary: **implemented and verified**, **implemented, not verified**,
**partially implemented**, **blocked**, **planned**. "Verified" means a test or a
gate exercises it and the result was observed, not that the code looks right.

Evidence at the time of writing: `cargo test` 138 passed, `npx vitest run` 154
passed, `npx tsc --noEmit` clean, `npm run build` clean, and the three browser
gates (`verify-fit`, `verify-chrome`, `verify-chassis`) green against the running
Windows build. The patch store was also verified across a real restart of the
app process, not only across a page reload, and the observatory through
the running build (readings, hover naming, press-to-open and fit at eight sizes).

## Analysis and metering

| Feature | Status | Evidence / limit |
| --- | --- | --- |
| Real-time spectrum, 56 bands, 2048-pt Hann FFT | Implemented and verified | `analysis.rs` computes it from the frames the player wrote to the device; gate F9 plays a 1 kHz tone and finds it at 1026 Hz |
| RMS, sample peak, low/mid/high energy | Implemented and verified | `analysis::Meter` tests the RMS and peak of a known sine and its crest factor; idle shows `—`, never a fabricated number |
| Playback level holds the value it is set to | Implemented and verified | `PlayerState::status` reports the level from the app's own atomic on every poll, including when nothing has been played and there is no engine to read it from; before that the idle status fell back to the default 0.7, so the slider — which follows the reported level — snapped back on the next 250 ms poll. `player::tests::the_playback_level_is_reported_before_anything_has_played` sets 0.42, 1.0 and 0.0 with no stream open and reads each back. Verified in the running build by clicking the Signal chain slider at 35 % with the mouse: it read 0.34 immediately and still read 0.34 after four more polls. The frontend also holds a level it has just sent until the engine reports the same one, so a poll that left before the drag cannot pull the thumb back under the pointer |
| Playback level remembered between launches | Implemented and verified | The engine's level is memory-only, so every launch played at 0.7 however often it was moved. The interface now keeps it with the other settings in the WebView's own storage (`audiorium.playback-level`): `usePlayer` starts at the remembered level, hands it to `set_playback_volume` once before a track opens, and writes it on every change, so the engine and the slider agree and the poll cannot pull the thumb back. Verified in the running 1.0.6 build: the level was pressed down to 0.52 (52 % · −5.7 dB) in the setup dialog, the app was quit and started again, and the new process reported `playback_status.volume` 0.52 with the slider drawn at 52 % before anything was touched |
| Analysis measures after the chain | Implemented and verified | The meter is fed the clamped output frames, so EQ, reverb, limiter and playback level all move the reading; gate F9 checks the level and peak describe one sine |
| Capture the chosen input device | Implemented and verified | `capture.rs` opens the single endpoint chosen on the Devices page in shared mode at the app's 48 kHz float stereo format and meters it with the same `Meter`; `AnalysisState` names its owner, so the panels show playback or the input and never an average. Verified live on this machine: `Voicemeeter Out B2 (VB-Audio Voicemeeter VAIO)` opened, published `source: input` with real signal, and a capture the user stops and starts by hand is no longer needed: another device, another output or a change of listening replaces the running capture. Verified live: a running capture of `Voicemeeter Out B2` was replaced by the loopback of `Voicemeeter Input` with no stop press, and one stop released the panels |
| Capture what an output is playing (loopback) | Implemented and verified | The input list also carries every output, opened as Windows' loopback of that endpoint: an application keeps its own output and still appears in the panels. No driver and no Secure Boot change. Verified in the running app: a 440 Hz tone played by Windows' own player into the default output measured `PEAK BAND ≈ 468 Hz`, `−10.9 dBFS` RMS, `−22.3 / −12.0 / −25.4 dBFS` bands; stopping returned the route to idle, and a silent loopback reads as the floor instead of the last curve |
| Listen to what is captured, to a chosen output | Implemented and verified | `Monitor` in `capture.rs` renders a capture's frames through a `Chain` built from the same `ChainState` and `SpatialConfig` playback uses, into the output chosen on the Devices page; the toggle is remembered (`audiorium.monitor`) and the route card names the output it is heard on. A capture played back into the output it reads is refused with the reason shown, and the capture keeps metering. The capture thread only queues frames; the monitor's own thread owns the render stream, keeps the device fed, fills with silence instead of replaying stale frames and fades the first 10 ms in, so a late packet is a gap rather than the clicks and bursts of static the first version produced (it wrote only the space the device reported and dropped the rest of each packet). Verified live on this machine: the monitor wrote a 440 Hz tone to `Voicemeeter Input (VB-Audio Voicemeeter VAIO)` with nothing else playing, that output's own loopback measured it back at 0.41 RMS with a peak of 0.5, and the longest silent run inside the tone was **1 frame** — no dropouts |
| Capture from the Audiorium device | Not verified end to end here | The endpoint exists in the test-signing VM and is proven by `Probe.cs`; this host cannot load the driver while Secure Boot is on, so capture from it is untested on this machine |
| Level history trace | Implemented and verified | `useAudioHistory` over status polls, bounded to 240 frames |
| Integrated / short-term loudness, LRA | Not implemented | No LUFS anywhere in the interface |
| True peak (dBTP) | Not implemented | Sample peak only; labelled as such |
| Goniometer, correlation and L/R balance | Implemented and verified | `analysis::Meter` keeps each channel's energy, their cross term and the window's mid/side pairs; tests pin identical channels to the vertical axis, an inverted pair to the horizontal one, quadrature to 0 correlation and silence to 0 without a NaN. The display is a phosphor canvas (fade + additive Lissajous path, no per-poll DOM) whose samples are drawn against full scale in their own direction, so hard-panned frames reach the ring and the whole circle is reachable instead of the mid/side diamond, a paused track freezes that trace, the spectrum surface and their readouts where they are and carries on from them on resume, while a stop fades them out over a second instead of blanking; the running app drew a 240-point window from a 4 dB-left file at `+0.95` / `20 % LEFT` |
| Spectrogram, configurable FFT size | Not implemented | The phase display is a per-window goniometer, not a scrolling spectrogram |
| Offline file analysis | Not implemented | Analysis runs on what is playing, not on a file chosen without playing it |
